# คอมโบลับของเครื่องรางและสัตว์คู่ใจ

Feature เพิ่มตามคำขอผู้ใช้วันที่ 2026-10-10: เมื่อสวมเครื่องรางหรือสัตว์ที่เข้าชุดกัน เกิดผลพิเศษที่ผู้เล่นค้นพบเองผ่านการเล่นและเอฟเฟกต์ รวมถึงชุดข้ามสาย เอกสารนี้เป็นแบบสำหรับ developer ในแผนกลาง ชุดนำร่อง SC01/SC02/SC03/SC11/SC13 implement ในเครื่องแล้ววันที่ 2026-10-10; ยังไม่ได้ deploy หรือติดตั้ง SQL production ดู [combo-implementation.md](combo-implementation.md) สำหรับ contract และหลักฐานล่าสุด

## ประสบการณ์ที่ต้องได้

ผู้เล่นลองใส่ของแล้วสังเกตว่าภูตหันมองเครื่องรางหรือมีแสงตอบรับ เมื่อทำงานที่เกี่ยวข้องจึงเห็นพฤติกรรมพิเศษ เช่น นากพาปลากลับมาให้เริ่มสู้รอบใหม่ใกล้ฝั่งขึ้น แสงต้องเกิดในจังหวะที่ผลทำงานจริง และทำให้เข้าใจว่าชุดนี้มีความสัมพันธ์กัน ผู้เล่นเล่าให้เพื่อนลองได้โดยเกมไม่เฉลยทุกชุดตั้งแต่ต้น

ไม่มีหน้ารวมคอมโบที่ยังไม่พบ ไม่มีช่องเงาพร้อมจำนวนชุดที่ขาด และไม่ขึ้นคำแนะนำตรง ๆ ว่าให้ใส่ A+B หากค้นพบแล้วมีบันทึกส่วนตัวที่บอกชุดที่ใส่ ผลที่สังเกต และข้อจำกัดที่รู้แล้วได้ ผู้เล่นต้องเข้าใจผลที่ใช้วางแผนได้หลังพบ ไม่ให้ความลับเป็นเหตุให้เสียทรัพยากรโดยไม่รู้กติกา

## ขอบเขตและช่องสวมใส่

- ชุดสองชิ้นรองรับ `เครื่องราง + เครื่องราง` หรือ `เครื่องราง + สัตว์/ภูต` ทั้งสายเดียวและข้ามสาย
- ชุดสามชิ้นรองรับ `เครื่องราง 2 + สัตว์/ภูต 1` เป็นความลับที่พบยากขึ้น ไม่เพิ่มช่องอุปกรณ์
- สัตว์สองตัวพร้อมกันเป็นชุดที่ผิดกติกา ไม่มีการจำสัตว์ที่เคยใส่แล้วนับเป็น active หลายตัว
- ต้องเป็นของที่ได้รับจริงและสวมอยู่ การมีอยู่ใน collection เฉย ๆ ไม่ทำงาน
- รุ่นแรกไม่ใช้ passive things เป็นส่วนประกอบคอมโบ เพื่อรักษาการเลือก loadout; effect เดิมของ things ยังทำงานและต้องนำมาประเมิน balance
- ไม่มีคอมโบที่ต้องใช้บัญชีหรือเพื่อนอื่นสวมของคู่กันในรุ่นแรก งาน social ได้ประโยชน์กับเพื่อนจากผู้ใช้ชุดเดียวตามสิทธิ์ของ action

ให้ registry รองรับ C+C แม้ pilot แรกใช้ C+F กรณีทดสอบต้องมี C+C และ C+C+F ด้วย ห้ามให้ engine ผูกกับจำนวนสองชิ้นหรือกับสายเดียวเท่านั้น

## กติกาการเกิดผลและการซ้อน

คอมโบเพิ่มทางเลือก จังหวะช่วยเหลือ หรือการอ่านสถานการณ์ ไม่ยกเลิกการเล่นหลักและไม่ต้องมีคอมโบเพื่อทำ progression ปกติ คะแนน OP ให้ประเมินทั้ง loadout โดยรวมเทียบกับชุดเดียวกันที่มีเพียง effect เดิม

1. ตรวจชุดที่ normalized แล้วและ server capability ก่อนแสดงสัญญาณ การใส่ของไม่กิน quota และไม่แจก reward
2. งานหนึ่ง action ใช้ loadout ตอนเริ่ม และต้องยังสวมองค์ประกอบที่ต้อง active ตอน trigger ผล ถ้าถอดระหว่างงาน ผลคอมโบพัก/ไม่จ่าย ไม่สลับกลางเกมแล้วได้คอมโบย้อนหลัง การ resume ตรวจใหม่แต่ไม่ reset usage หรือ checkpoint
3. action ที่ต้องใช้ภูตยังตรวจผลเดิมของภูตตามกฎฐาน การ snapshot คอมโบไม่อนุญาตให้ effect สัตว์หลายตัวเกิดใน action เดียว
4. effect ชนกับ buff/tool เดิมในมิติเดียวกันใช้ strongest ไม่บวกซ้ำ ข้อยกเว้นต้องระบุใน contract โดยเฉพาะ cap ผลผลิต แรง growth และ retry
5. ถ้าชุดใหญ่ครอบชุดเล็กและ effect กลุ่มเดียวกัน ให้ชุดใหญ่แทนชุดเล็ก ไม่หักสอง quota รุ่นแรกอนุญาตผลคอมโบที่เป็น gameplay สูงสุดหนึ่งชุดต่อ action; เลือก priority ที่กำหนดไว้โดยไม่ขึ้นกับลำดับ charms ใน array
6. ผลที่ยังไม่เข้าเงื่อนไขหรือ quota หมดไม่ตัดสิทธิ์ชุดอื่นที่ยังใช้ได้ ไม่มีการเลือกชุดใหญ่ที่ใช้ไม่ได้แล้วทำให้ชุดเล็กหายไปโดยไม่มีเหตุผล
7. ปฏิเสธเพราะ full bag/สิทธิ์/ทรัพยากรไม่พอไม่กิน quota ถ้าคอมโบช่วย retry แล้วเริ่มเล่นรอบช่วยจริง ให้หักสิทธิ์ ณ จุดนั้นไม่ว่ารอบช่วยจะชนะหรือแพ้
8. ห้ามผลคอมโบกระตุ้นตัวเองหรือคอมโบอื่นวนซ้ำ เช่น second catch ไม่เปิด second catch ใหม่, ผลิตของโบนัสไม่ถือเป็น action ใหม่, โบนัสคืนแรงไม่เปิดโบนัสคืนแรงอีกรอบ
9. การค้นพบ quota การใช้ และ reward ถูกบันทึก atomic กับ action; reconnect/retry จ่ายผลและประกาศค้นพบครั้งเดียว ใช้ identity ของ action จากฐานเดิมถ้ามี

## การค้นพบและเอฟเฟกต์

| จังหวะ | สิ่งที่ผู้เล่นเห็น | สิ่งที่เกมบันทึก |
|---|---|---|
| สวมชุดเข้ากันครั้งแรก | แสงตอบรับสั้นจากองค์ประกอบที่สวม 600–900 ms และภูตหันมอง; ไม่เฉลยชื่อผล | cue seen แบบ cosmetic ได้ ไม่ถือว่าค้นพบผลจริง |
| เข้า action ที่เกี่ยวข้อง | cue เฉพาะบริบท เช่น หางนากกับทุ่นเรือง; ผู้เล่นยังเล่นเกมตามปกติ | ตรวจ eligible state กับ quota ฝั่ง server |
| ผลพิเศษทำงานจริงครั้งแรก | เอฟเฟกต์เฉพาะชุด 800–1200 ms พร้อมข้อความเช่น “นากจำเส้นทางของปลาตัวนี้ได้!” | discovery ของ account พร้อม combo key/version และ action identity |
| ใช้ซ้ำหลังพบ | เอฟเฟกต์สั้น 250–450 ms บอกผลที่เกิด ไม่มี toast ยาวทุกครั้ง | quota/ผลใน action ตาม contract |
| เปิดบันทึกส่วนตัว | แสดงเฉพาะชุดที่พบ สูตรที่เราสวมตอนพบ ผล และข้อจำกัดที่ใช้งานได้ | ใช้ discovered records ของเรา ไม่แจก registry ชุดที่ไม่พบ |
| หมดสิทธิ์หรือเงื่อนไขไม่ครบ | หลังเคยพบแล้วบอกข้อจำกัดที่เกี่ยวข้องเมื่อพยายามใช้; ก่อนพบไม่แจ้งสูตรที่ขาด | ไม่ปลอม effect ว่าจ่ายโบนัสสำเร็จ |

cue ตอนสวมมีได้สำหรับชุดที่พร้อมใช้งานและเปิด capability แล้ว แต่ discovery ต้องเกิดเมื่อได้รับผล gameplay จริง ใส่แล้วถอดวนไม่เปิดบันทึกหรือได้รางวัล discovery ไม่มี XP/coins จากการพบในรุ่นแรก

เอฟเฟกต์ต้องแตกต่างจาก buff aura เดิม ใช้รูปทรง/การเคลื่อนที่ขององค์ประกอบสองชิ้นเชื่อมกัน สีอย่างเดียวไม่พอ เสียงเป็นส่วนเสริม ปิดเสียงแล้วยังเข้าใจได้ reduced motion ให้แสดงภาพนิ่งและข้อความแทน การเกิดแสงไม่บัง input/เกม ต้องมีข้อความเข้าถึงได้และไม่ทำให้ particle ซ้อนกันทั้งหน้าจอ

เราใช้ [TownBuffFx.tsx](../../../components/town/TownBuffFx.tsx) และ vfx ของเกมเป็น reference เท่านั้น ของเดิมแสดงว่ามี buff ไม่ได้ยืนยันว่าผลคอมโบทำงาน จึงควรมี cue/event ของคอมโบแยกและไม่เรียกเอฟเฟกต์สำเร็จจาก client ที่เดาสูตรเอง

เพื่อนใกล้ตัวอาจเห็น burst ที่ผลเกิดแล้วได้ ใช้ VFX ที่ส่งเฉพาะพื้นที่กับ event ที่ตรวจแล้ว ไม่ broadcast สูตร loadout หรือบันทึกคอมโบที่ยังไม่พบของ account อื่น ไม่มีการเปิดชื่อ secret combo ใน tooltip ของคนที่ยังไม่ค้นพบ

## ทาง implement และขอบเขตความลับ

“ลับ” หมายถึงไม่เฉลยใน UI, public notes หรือส่ง registry ทั้งหมดให้ client ผู้เล่นอาจแบ่งปันการค้นพบกันเองได้ เอฟเฟกต์ที่ส่งให้ client ย่อมสังเกตได้ เป้าหมายไม่ใช่รับประกันว่าผู้เล่นไม่มีทางอนุมานสูตร

- เก็บ requirement/predicate/priority/numbers ของคอมโบใน rule source ที่รันฝั่ง server และข้อมูล private ที่ game rules อ่านได้ ไม่ import ลง client bundle หรือส่งผ่าน public catalog
- ใช้ catalog projection ที่ตัด secret registry ออก ตรวจจริงว่า endpoint ที่ client อ่านไม่ส่งคู่ทั้งหมด ไม่สมมติว่า catalog ปัจจุบันเป็น private
- client รับเฉพาะ capability, cue ที่เกี่ยวกับชุดปัจจุบัน, ผล action ที่ตรวจแล้ว, และบันทึกที่ account นี้ค้นพบ ใช้ opaque visual cue สำหรับชุดยังไม่พบ ไม่ส่ง failure reason ที่แจกสมาชิกสูตรที่ขาด
- Minigame effect ที่ต้องแสดงก่อนจบ เช่น correction window/sonar ต้องรับ action-bound modifier จาก server ตอนเริ่มเกมและตรวจใช้ในผลด้วย ส่วนโบนัสจ่ายที่ server ตอน commit ไม่ใช้การกดดู animation เป็นหลักฐานสำเร็จ
- Trial keeper ใช้ rule source เดียวกันเท่าที่ทำได้ แต่ asset/client build ของ production ต้องไม่พ่วง registry ของ trial ที่มีสูตรทั้งหมด ตรวจ import graph ก่อน release
- รุ่นแรกเสนอ state namespace แยก `combos` สำหรับ discoveries/usage/action state ห้ามใช้ `gifts.used` โดยไม่ขยายการตรวจ IDs เพราะ `usedOf` ปัจจุบันยอมรับ GiftId เท่านั้น ชื่อและ shape จริงปิดใน COMBO-CORE
- usage ผูก combo/pool ไม่ใช่ลำดับเครื่องราง SC01/SC13 ใช้ shared pool แม้สลับชุด การปรับ rule version ไม่ reset usage ในวันนั้นโดยอัตโนมัติ
- มินิเกมและ record ที่ข้ามวันใช้วันเกม 05:00 Bangkok สำหรับ daily quota; ไม่แจก rescue เก่าให้ใช้ทั้ง quota ของวันเก่าและใหม่ action เดียวกัน ต้องกำหนดวันหัก ณ trigger ไว้ชัด

## จุดตรวจ balance

ตรวจชุดที่มีคอมโบเทียบกับชุดเดียวกันที่ยังไม่มีผลพิเศษ เพื่อแยกว่าคอมโบเพิ่มอะไร ไม่รวมผลเดิมเป็นความแรงของคอมโบซ้ำ เช่น SC05 ได้การเข้าหาเงียบ ไม่ใช่เดิน 2× เพิ่มอีกครั้ง หรือ SC13 เพิ่ม progress rescue ไม่ใช่เพิ่มทั้ง grace/bait/fish reward อีกชุด

ให้ทุกชุดมี signature เฉพาะ แม้ผลข้อมูลอาจ OP ต่ำกว่า rescue ผลลับควรสนุกโดยไม่กลายเป็นสูตรบังคับที่ทำให้คนไม่รู้สูตรเล่นอาชีพไม่ได้ อย่าเพิ่ม hidden multiplier ของรายได้/XP แบบไม่มีสัญญาณให้เข้าใจ

ทดสอบทุก effect ร่วมกับ passive things ที่เกี่ยวข้อง: star bait/pair mode, garden root/satellite, helper growth 3×/bell cap, forge one-hit/area powers, gnome/mandrake และ tools ที่ให้ hint เดียวกัน หากไม่มีประโยชน์เพิ่มเพราะ strongest ให้ไม่กิน quota หรือค้นพบเทียมจาก effect ที่ไม่ได้ทำงานจริง

## ลำดับ implement

1. COMBO-CORE: normalization/matcher ที่รองรับสองและสามชิ้น, effect selection, shared pools, private projection, discovery และ action lifecycle
2. COMBO-FX: equip response, eligible hint, committed burst และ discovered-only notebook รวมการปิดเสียง/reduced motion
3. COMBO-PILOT: SC01, SC02, SC03, SC11, SC13 ให้ครบ UI/RPC/tests เป็นชุดเล็ก ใช้อุปกรณ์เดิมแต่ต้องเปิด baseline gates ของสายก่อน
4. COMBO-CROSS: SC04–SC10, SC12 และ SC17–SC18 โดยแบ่งทำ 1–3 ชุด/แชทตามความพร้อมของ gameplay รวม C+C และ trio ที่มีผลจริง
5. COMBO-TIER10: SC14–SC16 หลังรางวัลที่ใช้อ้างอิงพร้อม เพิ่มชุดรุ่นถัดไปได้โดยใช้ contract เดิม
6. COMBO-REVIEW: matrix ของ loadout, duplicate/exclusion/economy, ความลับใน bundle/API และ playtest การค้นพบก่อนเข้า release

ไม่มี requirement ให้ใส่คอมโบครบทุกคู่ที่เป็นไปได้ 18 ชุดนี้เป็น backlog ตั้งต้นที่ครอบคลุมทั้ง 9 สาย ไม่ใช่ 18 รางวัลเพิ่มในเป้าหมาย 90 และไม่แทน usable item quota ของ adventure-expansion

## Acceptance สำหรับทุกชุด

- ของครบแต่ไม่ได้สวมไม่ทำงาน, สวมผิด kind/ไม่ owned ถูกปฏิเสธ, ลำดับ charms ไม่เปลี่ยนผล, เกินสอง charms/สัตว์หลายตัวถูก normalize ตามกฎเกม
- ทดลอง C+C, C+F, C+C+F และ shared-pool subset; active effect ไม่ขึ้นกับ prior loadout และการถอดแล้วใส่ไม่ reset quota
- valid trigger จ่ายผลครั้งเดียว, วัน reset/หลาย devices/retry/resume/full bag/failed action เป็นไปตาม contract
- trigger ที่ยังไม่เกิดไม่บันทึก discovery; discover ครั้งแรกพร้อม effect จริง, reconnect ไม่ toast ซ้ำ; unknown notebook/API ไม่มีสูตรที่ยังไม่พบ
- same-effect strongest, shared caps และไม่มี reentrant second-catch/refund/โบนัสจากโบนัส
- สังเกตเอฟเฟกต์ได้บนมือถือ ปิดเสียง/reduced motion ยังเข้าใจ ไม่บังเกม และผู้เล่นอื่นไม่ได้ข้อมูลส่วนตัวที่ไม่ควรเห็น
- ตรวจ production client imports, catalog projection และ runtime responses ไม่ส่ง secret registry; ดู source file ใน repo ไม่ถือเป็นการตรวจ bundle
- มีหลักฐาน local/tests/deploy/SQL/live แยกกัน และ handoff ระบุ combo key, effect group, quota pool, priority, cue family และ rule version
